# 5. ENTERPRISE-GRADE SECURITY REQUIREMENTS

IMPORTANT:

Security must be IMPLEMENTED in the actual application code.

Do not merely describe security features in documentation.

Do not claim that the website is 100% hack-proof.

Use secure-by-default principles throughout the complete application.

---

## A. SECRET & API KEY SECURITY

1. NEVER expose Gemini API keys, API keys, database credentials, passwords, JWT secrets, private tokens, service-account credentials, or other secrets in React/frontend/client-side code.

2. Store all secrets only in server-side environment variables or a secure secret-management system.

3. Never hardcode secrets inside React components, TypeScript files, JavaScript files, HTML, CSS, public assets, or Git repository.

4. Create a secure server-side API/proxy layer for all third-party APIs that require secret credentials.

5. Do not send secret API keys to the browser.

6. Add a proper `.gitignore` and ensure `.env` files and secret files are never committed to Git.

7. Do not expose secrets through API responses, console logs, error messages, source maps, or client-side configuration.

---

## B. ADMIN PANEL SECURITY

8. Create a secure Admin Panel only if an administrative management system is implemented.

9. Admin Panel must require authentication.

10. Do not allow visitors or normal users to access administrative functions.

11. Implement role-based access control.

12. Separate:

* Public Visitor
* Admin
* Super Admin, only if required

13. Protect every admin API endpoint on the SERVER, not only through frontend route protection.

14. Never rely only on hiding an admin button or frontend route.

15. Unauthorized requests to admin APIs must return an appropriate unauthorized/forbidden response.

16. Implement secure logout.

17. Implement session expiration.

18. Prevent session fixation and unauthorized session reuse.

---

## C. PASSWORD SECURITY

19. Never store passwords in plain text.

20. Use a strong password hashing algorithm such as Argon2id or bcrypt with an appropriate work factor.

21. Never return passwords or password hashes to the frontend.

22. Do not log passwords.

23. Implement login attempt protection/rate limiting.

24. Do not reveal whether a specific username/email exists through overly detailed authentication error messages.

25. If password reset is implemented, use secure single-use, time-limited reset tokens.

---

## D. SESSION & COOKIE SECURITY

26. If cookie-based authentication is used, configure cookies with:

* HttpOnly
* Secure
* SameSite

27. Never store sensitive authentication tokens in insecure browser storage when a safer server-side/session-cookie architecture is available.

28. Implement proper session expiration.

29. Invalidate sessions/tokens when users log out.

30. Protect authenticated endpoints from unauthorized session use.

---

## E. DATABASE SECURITY

31. Never expose database credentials to the frontend.

32. Use server-side database access only.

33. Use parameterized queries or safe ORM/database APIs.

34. Protect against SQL injection and NoSQL injection.

35. Validate all database inputs on the server.

36. Never return unnecessary private database fields through public APIs.

37. Apply least-privilege permissions to database users.

38. Keep private administrative records inaccessible to public APIs.

39. Add appropriate database indexes and limits to prevent abusive queries.

40. Do not store sensitive information unless it is actually required.

---

## F. INPUT VALIDATION & SANITIZATION

41. Validate every user-controlled input on the SERVER.

42. Never trust frontend validation alone.

43. Validate:

* Contact forms
* Career forms
* Admin forms
* Search fields
* Project data
* Gallery data
* Company information
* File metadata
* Query parameters
* URL parameters

44. Sanitize user-controlled content before rendering it as HTML.

45. Protect against:

* XSS
* HTML injection
* SQL injection
* NoSQL injection
* Command injection
* Path traversal

46. Use safe output encoding wherever user-provided content is displayed.

---

## G. PHOTO & FILE UPLOAD SECURITY

47. If image/file upload is implemented, validate files SERVER-SIDE.

48. Do not trust the file extension supplied by the user.

49. Validate actual MIME type/file signature where practical.

50. Allow only explicitly approved file types such as:

* JPG/JPEG
* PNG
* WEBP
* PDF

Only enable file types actually required.

51. Reject executable and dangerous file types.

52. Set strict maximum file sizes.

53. Set reasonable image dimension limits.

54. Generate random safe filenames on the server.

55. Never use the original user-provided filename directly as a server path.

56. Prevent path traversal such as:

`../`

`..\\`

and encoded variants.

57. Store uploaded files outside executable server directories where possible.

58. Prevent uploaded files from being executed as server-side code.

59. If practical, re-process uploaded images before serving them publicly.

60. Do not expose internal filesystem paths.

61. Do not allow users to overwrite arbitrary existing files.

62. Protect private uploads from unauthorized access.

---

## H. RATE LIMITING & ABUSE PROTECTION

63. Implement server-side rate limiting for:

* Login
* Password reset
* Contact form
* Career form
* Admin APIs
* File uploads
* Public APIs
* Gemini/API proxy endpoints

64. Prevent brute-force login attempts.

65. Prevent excessive API requests.

66. Add request size limits.

67. Add appropriate timeout limits.

68. Add spam/abuse protection to public forms.

69. Do not rely only on client-side throttling.

---

## I. CORS SECURITY

70. Configure CORS using an explicit allowlist of trusted origins.

71. Do NOT use unrestricted:

`Access-Control-Allow-Origin: *`

for sensitive authenticated APIs in production.

72. Allow only required HTTP methods and headers.

---

## J. CSRF PROTECTION

73. Protect state-changing authenticated requests against CSRF where cookie-based authentication is used.

74. Use appropriate CSRF tokens and SameSite cookie protections where needed.

75. GET requests must not perform destructive state-changing operations.

---

## K. SECURITY HEADERS

76. Configure appropriate HTTP security headers, including where compatible:

* Content-Security-Policy
* X-Content-Type-Options
* Referrer-Policy
* Strict-Transport-Security
* Frame protection / frame-ancestors
* Permissions-Policy

77. Configure the headers correctly for the application's actual resources and third-party services.

78. Do not introduce a CSP that breaks the application unnecessarily.

---

## L. HTTPS / TRANSPORT SECURITY

79. Production deployment must use HTTPS.

80. Never transmit passwords, authentication credentials, or sensitive information over plain HTTP.

81. Configure secure cookies when HTTPS is enabled.

---

## M. ERROR HANDLING

82. Never expose:

* Stack traces
* API keys
* Database credentials
* Internal filesystem paths
* Server configuration
* SQL queries
* Tokens
* Passwords
* Sensitive debugging information

to normal users.

83. Implement safe production error messages.

84. Log detailed errors only on the secure server side.

---

## N. LOGGING & AUDIT SECURITY

85. Add security/audit logs for important administrative events, such as:

* Admin login
* Failed login attempts
* Logout
* Admin changes
* Project changes
* Gallery changes
* Company information changes
* User/role changes
* File uploads/deletions

86. NEVER log:

* Passwords
* API keys
* Authentication tokens
* Database credentials
* Other secrets

---

## O. PUBLIC FORM SECURITY

87. Secure Contact and Career forms against spam and abuse.

88. Validate email addresses and required fields server-side.

89. Apply request size limits.

90. Sanitize submitted data.

91. Do not expose private applicant/contact information through public APIs.

92. Protect submitted data from unauthorized access.

---

## P. FRONTEND SECURITY

93. Do not place sensitive business logic or authorization decisions only in React/frontend code.

94. Frontend route guards may be used for user experience, but SERVER-SIDE authorization must always be enforced.

95. Do not expose hidden admin routes as a security mechanism.

96. Avoid dangerous HTML rendering such as unrestricted `dangerouslySetInnerHTML`.

97. If HTML rendering is absolutely required, sanitize it using a trusted sanitization approach.

---

## Q. DEPENDENCY & PACKAGE SECURITY

98. Use only required npm packages.

99. Avoid abandoned or unnecessary dependencies.

100. Keep dependencies updated.

101. Check dependencies for known security vulnerabilities before production.

102. Do not install packages from untrusted sources.

---

## R. SERVER & DEPLOYMENT SECURITY

103. Run production services with the minimum required privileges.

104. Do not expose unnecessary ports or services.

105. Do not expose development/debug endpoints in production.

106. Disable verbose development debugging in production.

107. Do not expose source maps publicly if they reveal sensitive information.

108. Keep server and runtime versions reasonably up to date.

109. Configure secure environment variables in the deployment platform.

---

## S. SECURITY TESTING BEFORE DEPLOYMENT

110. Before declaring the application production-ready, perform a security review of the complete codebase.

111. Verify that no API key or secret is exposed in frontend bundles.

112. Test unauthorized access to admin routes and APIs.

113. Test authentication and logout.

114. Test rate limiting.

115. Test input validation.

116. Test XSS protections.

117. Test file upload restrictions.

118. Test path traversal protection.

119. Test CORS configuration.

120. Test security headers.

121. Test HTTPS configuration.

122. Test that private database data cannot be accessed publicly.

123. Check npm dependencies for known vulnerabilities.

124. Fix all HIGH and CRITICAL security vulnerabilities before production.

---

## T. SECURITY IMPLEMENTATION REPORT

125. After implementing these requirements, provide a concise SECURITY IMPLEMENTATION REPORT.

126. The report must list:

* Authentication implementation
* Authorization implementation
* API security
* Secret management
* Database security
* File upload security
* Rate limiting
* Input validation
* XSS/CSRF protection
* CORS configuration
* Security headers
* HTTPS requirements
* Logging/auditing
* Dependency security
* Security testing performed

127. Clearly identify which files/components contain each major security implementation.

128. Do not claim "100% secure", "unhackable", or "impossible to hack".

State honestly what security controls have actually been implemented.
